# Project 2 · DriveVoice Agent Lab — 项目总文档

**一句话定位**：基于开源车载语音 Agent（QwenAudio/qwen-audio-agent 智能座舱示例，Apache-2.0）的二次研究项目——我以产品评测与实验为主线，完成了评测集扩展、官方基准复现、bad case 五层归因、四组消融实验与一套安全确认策略，全部结论来自真实运行数据。

**诚实边界（面试必读）**：基座框架、四进程架构、38 个场景工具与官方基准为上游开源成果，**不是我从零开发的**。我的个人贡献是 R1–R5 五块工作（见第三节），简历与面试中均按此口径表述。本项目为个人自主项目，与任何公司实习无关。

---

## 一、为什么选这个基座

针对 Tesla 语音 AI 产品实习 JD（语音对话数据分析与 bad case 归因、LLM/Agent 全链路调研、PRD 与产品设计），我需要的是一个**能真实运行、带官方基准、可扩展评测**的车载语音 Agent，而不是玩具 Demo。该基座满足：

- 完整链路：全双工语音（可打断）+ 网关路由 + Agent 编排 + 车辆服务执行；
- 工业级评测资产：官方 Short 86 例 / Long 500 轮基准 + 前后台路由对照集，且公布了成绩可供复现校验；
- 与我 Project 1（DriveVoice 产品方案）同域：评测方法、归因框架、安全策略可以互相迁移验证。

备选淘汰记录：Pipecat（通用语音框架，无车载场景与基准）、LiveKit Agents（基础设施过重）、xiaozhi-esp32-server（保留为语音链路学习参考）。

## 二、基座架构速览

- **四进程**：Client（5173）/ Gateway（18888）/ Agent（3020）/ Service（3010）。
- **前后台双工具面**：38 个工具按域路由——车控/音乐/导航/天气/自定义技能走前台（MCP 直达，低延迟），闪购走后台（A2A → Agent 编排，适合多步任务）；路由表 `surface-routing.json` 可配置。
- **三套人设**：action（高效）/ sharp / healer（治愈，默认）。人设与任务层解耦，有契约测试禁止人设携带任务规则。
- **官方基准**：Short 86 例（每例含多轮对话、期望工具调用、期望最终状态）、Long 10 例 × 50 轮、surface-compare 46 例。官方公布：Short 整例 97.67%~98.84%、Long 逐轮约 98.6%、前台/后台延迟 1.480s vs 3.560s。

## 四、评测设计说明

- **为什么扩这四个套件**：官方基准以"指令明确、单意图"为主，而真实车载语音的难点在四种情形——用户说一半改口（打断纠错）、ASR 识别噪声（同音/结巴/重复/数字）、高风险动作的安全确认、含蓄表达的多意图拆解（"有点闷"）。这四类恰与 Tesla JD 的"语音对话数据分析与 bad case 归因"对齐。
- **指标口径**：整例通过率（严格：调用序列与最终状态全对）与对齐逐轮准确率（允许参数上位集与顺序对齐）双口径并行；安全套件另设"确认率"与状态检查点；所有口径差异在归因报告中显式说明，避免用单一数字误导。
- **文本模式的边界**：扩展套件测的是轮级纠错语义，**不是**声学层面的真打断（真打断需语音链路，本机环境不具备）——文档与面试均按此说明。

## 六、Bad case 归因（R3，要点）

扩展集失败的五层分布：**生成-安全 47% > 规划 29% > 理解 14% > 执行 8% > 感知 4%**。

跨模型一致性失败（plus 与 flash 同构出现，属系统性问题）：
1. 安全确认全军覆没：12 个 L2 动作两模型均首轮直执，确认率 0%；取消不被尊重、催促可绕过、换目标后执行旧目标；
2. 同音地名"萧山鸡场"两模型均未纠错（感知层）；
3. 抢先执行：途经点删除指令被模型在上一轮"预演"执行（规划层）；
4. 恢复播放工具选择一致出错（执行层，toggle vs play）。

其他典型：模糊意图的零执行与只做一半（"有点闷"只开通风、漏风量）、歧义选错域（"快没电了"搜共享充电宝）、目的地过度具体化（"机场"→"杭州萧山国际机场"，三处复现）、Long 高分心场景多出 5 次调用、50 轮尾段状态跟踪衰减。

## 七、消融结论（R4，要点）

1. **思考开关**：开思考对齐逐轮准确率 0.83 vs 关 0.74，但耗时约 2.5×、单次调用 token 约 28×（747 vs 26）；模糊场景关思考反而略好；安全确认两模式均 0%。→ 动态思考策略（简单指令关、复杂多意图开）值得做。
2. **安全软约束**：R5 协议文本作附加系统指令后，安全套件 3/15 → 13/15，L2 拦截 11/12；唯一泄漏是"问了但同轮先执行"的部分服从。→ 软约束作第一道防线、执行层硬拦截作最后防线（详见 R5 文档实测回填）。
3. **人设**：治愈/高效两套人设对工具调用成败与回复长度均无显著影响——实测验证人设层与任务层解耦（零结果，但有机制解释）。
4. **前后台路由**：三层分解定位延迟差——纯执行 <1ms 无差，纯链路差几十 ms，含模型推理前台 3002ms vs 后台 9746ms（约 3.2×），**差距来自第二次模型推理**；46 例中网关实际委托后台 0 次，原子指令应走前台得到实证。

## 八、安全确认策略（R5，要点）

- **分级**：L0 只读直执 / L1 低风险直执 / L2 高风险先确认（后备箱、前备箱、充电口、鸣笛、关大灯、停导航、充电上限、车窗大幅开闭等）。
- **确认流规则**：确认只对同动作同对象有效；换对象重新确认；取消即终止；催促不构成确认；同句预先确认可直执。
- **两层防线（实测修正版）**：Prompt 协议（拦 11/12）+ Service 执行层硬拦截（拦剩余泄漏）；硬拦截同时可审计、可回归（每条策略都映射到安全套件用例）。

## 九、产品结论与下一步路线

1. **执行层安全守卫**（最高优先级）：在 Service 层对 L2 工具加确认状态机，未确认的调用直接拒绝并回提示；用安全套件做回归门禁。
2. **行动阈值校准**：过度执行与含蓄意图零执行同源——需要"场景化行动策略"：明确指令防多调（执行前状态查询白名单）、含蓄意图给默认动作组合（闷→通风+风量）并在回复中可撤销。
3. **目的地归一化**：执行层做 POI 简称→标准名映射，消除"过度具体化"导致的状态不一致，不指望模型逐字复述。
4. **ASR 后纠错**：导航域结合城市 POI 词典做同音纠错（机场类高频地名优先）。
5. **动态思考**：按意图复杂度路由思考开关，平衡 2.5× 时延成本。

## 十、局限（主动声明）

1. 文本模式评测，不含真实 ASR/TTS 声学链路与真打断；语音侧结论仅限轮级语义。
2. Service 为模拟执行器（状态机），非真实车辆信号；安全策略是静态分级，未接入车速/挡位（R5 文档已注明量产需细分）。
3. 扩展集为自研用例，期望调用由本人按官方格式设定，存在单标注者偏差；已用官方校验器 + 金标回放降低格式与状态断言错误。
4. 路由延迟绝对值受本机公网 API 环境影响，只引用比值与分层结论，不引用绝对值与官方值直接对比。
5. 模型为服务别名（未锁定版本快照），跨日复跑可能有小幅波动；人设消融在文本模式下回复样本有限，结论限于工具调用层。
6. 免费额度曾导致两轮运行作废并剔除（Long-max、扩展集 flash 首跑），全部有效数据均来自付费模式完整运行，报告文件可查。

## 附录 C · 面试 Q&A（要点版）

**Q1：这个项目是你自己做的吗？框架是你写的吗？**
不是。基座是千问开源项目（Apache-2.0），我 fork 后做评测扩展、复现、归因、消融和安全策略。我的代码改动只有三处（思考开关、按例工具域收窄、软约束注入开关），都在 fork 里有注释和报告留痕。我认为产品岗的价值在评测与决策，不在重复造框架。

**Q2：为什么扩这四个套件？**
官方集以明确单意图为主；真实车载语音的失败集中在改口、识别噪声、高风险确认、含蓄多意图——正对应 JD 的数据分析与 bad case 归因。四类分别测纠错语义、感知鲁棒性、安全行为、意图拆解。

**Q3：你的评测集凭什么可信？**
三重校验：官方 `assertBenchmarkCase` 校验器全过；服务金标回放 70/70（期望状态断言先被执行器验证）；复现官方基准与公布值一致（Short 差 1 例、Long 逐轮 99.2% vs 98.6%），证明链路无系统性偏差。局限是期望调用由我单人设定，已在文档声明。

**Q4：最有价值的发现是什么？**
安全确认的跨模型系统性缺失：两个模型、思考开/关三种配置下，L2 动作确认率都是 0%，且取消、催促、换目标三种边界全部失败。这说明它不是模型能力问题，而是产品层没有给确认协议——换模型解决不了，必须在产品/系统层补。

**Q5：Prompt 能拦 11/12，为什么还要执行层硬拦截？**
因为剩下 1 例是"问了但同轮先执行"——软约束的服从是概率性的。真实车辆上一次未授权开后备箱就是事故级问题。硬拦截可审计、可回归、与模型无关。两层是纵深防御，不是二选一。

**Q6：思考（thinking）对语音 Agent 是开好还是关好？**
看场景。开：逐轮准确率 +0.09、漏调用明显少；代价 2.5× 时延、单次调用 token 约 28×。车载是实时场景，我的建议是动态策略：简单直执指令关思考、复杂多意图开思考。安全场景两者都 0% 确认，别指望靠思考解决安全。

**Q7：前台/后台路由为什么差三倍？慢在哪？**
我用官方对照工具做了三层分解：纯执行 <1ms 无差；纯链路只差几十 ms；差距几乎全在第二次模型推理——后台要网关先决策委托、Agent 再推理一次。所以路由准则：原子指令走前台，多步任务（闪购这类需要编排和外部系统的）才值得付后台的延迟成本。46 例里网关实际委托 0 次，侧面印证。

**Q8：模糊意图为什么最难？你的解法？**
失败两极：要么过度澄清零执行，要么只做一半。它缺的是"含蓄表达→默认动作组合"的产品策略，而不是模型智商。解法：建场景动作包（闷→通风+风量、脚冷→座椅加热+方向盘加热），执行后在回复里给可撤销出口，把确认成本从执行前挪到执行后（仅限 L1 低风险）。

**Q9：'萧山鸡场'这类错误怎么修？**
这是感知层的同音地名问题，靠 Prompt 让模型纠错不可靠。工程化解法：导航域在 ASR 后处理挂 POI 词典纠错（同音/近音 + 城市上下文），高频地名（机场、火车站）优先；评测上我已经有对应用例可回归。

**Q10：整例通过率和逐轮准确率为什么差这么多（Long 5/10 vs 99.2%）？**
整例口径要求 50 轮全对，错 1 轮整例判负；逐轮对齐口径才反映真实能力。产品评测必须双口径：逐轮看能力水位，整例看"一次完整旅程零失误"的用户体验概率——两者回答的问题不同。

**Q11：如果让你把这个项目继续做下去，下一步是什么？**
按归因优先级：① 在 Service 层实现 L2 确认状态机（硬拦截）并用安全套件做 CI 回归；② 目的地归一化与 ASR 同音纠错两个工程修复，各有现成用例验证；③ 动态思考路由的 A/B；④ 接真实语音链路测声学打断（当前是文本轮级，这点我不夸大）。

**Q12：这个项目和你面的岗位（Tesla 语音 AI 产品实习）有什么关系？**
JD 的四块工作我都实做过一遍：语音产品评测设计（R1）、对话数据分析与 bad case 归因（R3）、LLM/Agent 链路调研与消融（R2/R4）、把结论落成策略文档（R5，相当于 PRD 的前置决策）。加上 Project 1 的完整产品方案，两个项目一个偏产品设计、一个偏实测实验，互相印证。
