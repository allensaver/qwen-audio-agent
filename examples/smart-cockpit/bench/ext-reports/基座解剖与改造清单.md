## 二、架构解剖：四个独立进程

```text
cockpit-client ── GCP 7.0 ──► cockpit-gateway ── A2A ──► cockpit-agent
      │                          │                         │
      │ HTTP/SSE                │ frontend MCP            │ backend MCP
      │ 业务状态                 │ 车控/导航/音乐/天气/技能 │ 闪购
      ▼                          ▼                         ▼
                         cockpit-service
                         单一场景状态与工具执行
```

关键设计（面试要点）：

1. **前台/后台分离**：前台（client + gateway）负责实时对话和低延迟工具直调；后台 agent（默认 qwen3.8-flash）处理闪购、新闻检索等异步长任务。后台干活时前台照常聊天——这是全双工体验的工程实现方式。
2. **对话面与业务面分离**：车辆/导航/音乐等状态只有一个来源（cockpit-service）；Gateway 不理解车辆业务对象，只转发对话与工具调用。换座舱业务不用改对话层，换对话模型不用改业务层。
3. **两个 MCP 工具面按领域路由**：`surface-routing.json` 决定每个领域在前台还是后台执行，同一领域只暴露在一侧；改一行配置即可把整个领域（如导航）从前台挪到后台——这是现成的消融实验开关（见 R4）。
4. **记忆属于对话面**：长期记忆由 Gateway 的 MemoryProvider 管理（Markdown 存储），与座舱业务状态分开；后台 Agent 另有最多 50 轮的任务短期记忆。

## 四、Prompt 解剖：人设层与行为层是分开的

- 前台人设只有 3 个 Markdown 文件，每个仅 11 行：`action`（高效干练）、`sharp`（犀利有锋芒）、`healer`（温柔关怀，默认）。结构统一：Identity / Personality / Conversation style。
- 有专门的契约测试保证：**人设文件里不许写任务路由规则**。也就是说，人设只管语气，不管行为；工具该不该调、走前台还是后台，由工具描述、路由配置和 Harness 守卫决定。
- 面试可讲的产品洞察：车载场景把「说话风格」和「做事规则」解耦，人设可以一键切换、甚至给用户选，但安全与执行规则不随人设漂移。这是很多玩具级语音助手把所有东西塞进一个 System Prompt 做不到的。

## 五、官方评测集解剖（本项目最值钱的资产）

### 数据集构成（bench/cases/，JSONL，中文用例）

| 文件 | 条数 | 说明 |
|---|---|---|
| vehicle.jsonl | 24 | 车控单轮为主 |
| navigation.jsonl | 36 | 导航，含多途经点 |
| music.jsonl | 18 | 音乐 |
| weather.jsonl | 8 | 天气 |
| **Short suite 合计** | **86** | 1–3 轮/例，92 个需工具轮次 |
| mixed-long-context.jsonl | 10 例 / 500 轮 | 长对话：工具轮与闲聊（no-tool）轮交替，考多轮上下文与「不该调工具时别乱调」 |
| surface-compare.jsonl | 46 | 前台/后台执行面对比专用 |

每条用例的结构：`turns`（用户话术，可标注 `expect_no_tool`）+ `expected_calls`（turn_index / path 前后台 / 工具名 / 参数）+ `expected_final_state`（执行后车辆状态断言）。即同时考「调对工具」和「车真的变对了」。

### 打分口径（官方明确要求不许混叫一个「准确率」）

- **Full-case pass（整例通过率）**：最严——工具、参数、路径、轮次、no-tool 约束、最终状态全对才算过，一处错整例失败。官方 Short 结果：Realtime 前台 + Harness 97.67%（84/86），纯文本 qwen3.8-flash 98.84%（85/86）。
- **Per-turn tool behavior（逐轮工具行为准确率）**：长集口径，官方 99.80%（499/500），且必须同时公布 tool-required（250/250）与 no-tool（249/250）两个子项。
- 另有 strict sequence / aligned 两套工具参数准确率、final-state 成功率、延迟口径（从用户说完到最后一个工具返回：前台直调平均 1.480s vs 后台委派 3.560s）。

### 官方评测没有覆盖的（= 我们的改造空间）

1. **打断与纠错**：用例都是完整轮次文本，没有「播报中途被打断」「刚说完又改口（不对，去机场）」的套件——而这正是 Project 1 的核心功能。
2. **ASR 噪声鲁棒性**：输入是干净文本，没有同音字错误、口语重复、噪声导致的脏转写作为输入。
3. **安全确认**：没有「行驶中开后备箱/车门」类高风险动作应先确认或拒绝的策略测试集。
4. **回复质量**：官方明确把播报质量排除在默认分数外（需另设 judge rubric）——驾驶场景回复是否简短、可听懂，没有口径。
5. **模糊意图的组合执行**：「有点闷」「脚冷」这类需推理并组合多工具的表达覆盖有限。

## 七、阻塞项与注意事项

1. **需要用户提供**：阿里云百炼 DASHSCOPE_API_KEY（新用户有免费额度）。R2 及实时 Demo 依赖它；没有 Key 之前 R1（写用例）和解剖、教学准备都可以先行。
2. **可选**：高德地图 Key（AMAP）只影响客户端地图渲染，不影响评测。
3. **平台限制**：官方语音端到端 runner 需要 macOS 的 `say` + `ffmpeg`；本机是 Linux，所以语音链路我们走「文本评测 + 客户端实时体验」路线，口径上如实标注，不冒充跑过语音 runner。
4. **License 合规**：Apache-2.0，fork 改造需保留 LICENSE 与出处说明，简历与文档中明确基座来源。
